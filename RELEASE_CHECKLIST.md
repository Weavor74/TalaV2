# Tala Release Verification Checklist

Use this checklist to verify the Native Transparent Deployment strategy before cutting a major release. Tala is designed to bootstrap cleanly onto completely bare machines without destroying existing configurations.

## 1. Clean-Machine Pre-requisites
For rigorous testing, spin up clean virtual machines with **no pre-existing developer tools**.
- [ ] **Windows VM**: Fresh install of Windows 11 Home/Pro (ensure `winget` is available).
- [ ] **macOS VM**: Fresh install of macOS Sonoma/Sequoia (Homebrew should NOT be pre-installed).
- [ ] **Linux VM**: Fresh install of Ubuntu 24.04 LTS or Debian 12.

## 2. Windows Verification (`install-windows.ps1`)
- [ ] **Execution Policy Warning**: Does the script warn the user if the Execution Policy is set to `Restricted`?
- [ ] **Doctor Preflight**: Does the script correctly output `[FAIL]` for missing Node.js, Python, and PostgreSQL, and then proceed to install them?
- [ ] **Winget Installation**: Does `winget` correctly install Node.js, `uv`, and PostgreSQL silently?
- [ ] **Python Provisioning**: If no Python runtime is in `PATH`, does `uv python install 3.11` provide one for setup?
- [ ] **Database Bootstrap**: Does `bootstrap-db.ps1` correctly prompt for a Postgres password if default peer authentication fails, and succeed in creating the `tala` role and database?
- [ ] **Environment**: Is the `.env` file generated by `scripts/first_run.py` without overwriting an existing one?

## 3. macOS Verification (`install-macos.sh`)
- [ ] **Homebrew Prompt**: Does the script ask before running the official Homebrew installer if Homebrew is missing?
- [ ] **Dependency Resolution**: Does `brew install node@20 postgresql@16 uv` execute correctly and bind to the `PATH`?
- [ ] **Python Provisioning**: If no Python runtime is in `PATH`, does `uv python install 3.11` provide one for setup?
- [ ] **Database Service**: Does `brew services start postgresql@16` execute successfully before bootstrapping?
- [ ] **Database Bootstrap**: Does the script successfully execute `CREATE ROLE` and `CREATE DATABASE`?

## 4. Linux Verification (`install-linux.sh`)
- [ ] **Distribution Guard**: Does the script immediately halt with a clear error if run on an unsupported distro (e.g., Fedora, Alpine)?
- [ ] **Apt Installation**: Do `nodejs`, `npm`, and `postgresql` install correctly via `apt-get`?
- [ ] **uv Prompt**: Does the script pause and display a warning before executing the `astral.sh/uv/install.sh` remote script?
- [ ] **Python Provisioning**: If no Python runtime is in `PATH`, does `uv python install 3.11` provide one for setup?
- [ ] **Systemd Check**: Does `systemctl enable postgresql --now` succeed in waking up the Postgres daemon?

## 5. Launch & Lifecycle (`start-tala`)
- [ ] **Boot Check**: Does executing `start-tala` successfully boot both the Python backend and Electron UI?
- [ ] **Port Conflicts**: If you start a second instance of Tala, does the `doctor` explicitly halt the installation due to port `8000` or `8765` being `[IN USE]`?
- [ ] **Cleanup**: When you close the Electron UI window, does the shell script correctly trap the exit signal and kill the background Python process?

## 6. First-Run & Self-Test
- [ ] **Bootstrap Idempotence**: Does `uv run python scripts/first_run.py --self-test` succeed on a clean checkout and leave an existing `.env` unchanged on a second run?
- [ ] **Source Launch Repair**: If `.venv` or `.env` is removed, does `scripts/start-tala` run first-run setup before launching?
- [ ] **Tala Self-Test**: Does `npm run self-test` pass, including Python dependency imports, syntax checks, Python tests, Jest, and npm audit?
- [ ] **Chat Self-Test**: Does `/self-test` run from Tala chat and return a readable pass/fail summary? (npm audit was cleaned 2026-09-12 and now gates; `--no-audit` remains only as a faster inner-loop option.)

## 7. Packaging Verification
- [ ] **Changelog Written**: Does `CHANGELOG.md` have a non-empty `[Unreleased]` section? (`scripts/bump_version.py` refuses to release without one — it becomes the `release_notes` in version.json.)
- [ ] **Hashes Published**: After `scripts/build_bundles.py`, does `blockchain/public/version.json` carry a `sha256` entry for all three platform zips? (The updater's integrity check is skipped for any platform missing here.)
- [ ] **Lint Gate**: Do `npm run lint:js` and `npm run lint:py` pass, and `uv run pytest tests/test_size_ratchet.py`?
- [ ] **No Private Nodes in Bundles**: Does `uv run pytest tests/test_release_node_classification.py` pass? (persona-*, learning-*, benchmark-run-*, flow-*, corpus-* and _staging nodes are this install's data, not the product's.)
- [ ] **Unpacked Smoke Test**: Does `npm run pack` create a launchable app in `dist/`?
- [ ] **Current OS Package**: Does `npm run package` create the expected installer/archive for the host OS?
- [ ] **Packaged First-Run**: On first packaged launch, are `.env`, `.venv`, `vault/`, `data/`, and `scratch/` created under Electron `userData` rather than source-controlled folders?
- [ ] **Package Self-Test**: After installing the package on a clean machine, does `npm run self-test` or `/self-test` pass?
- [ ] **No Secrets in Bundles**: Does `uv run pytest tests/test_release_bundles_carry_no_secrets.py` pass against the freshly built bundle? (An earlier bundle shipped `.env`; a later one shipped `blockchain/data/poa_keys.json` with the live PoA private key.)

## 8. Security Rotations (one-time, before first public release)
These close out the exposures found in the 2026-09-09 production-readiness review. The code fixes landed 2026-09-12; these are the operator halves that cannot be done from the repo.
- [ ] **Rotate the PoA signing key**: The key pair in `blockchain/data/poa_keys.json` shipped inside `tala-windows.zip` (one known holder of the link, but the URL was unauthenticated). Delete the key file on the VPS, let `app.js` mint a fresh pair on restart, update the authority set, and remove the old zip from the webroot.
- [ ] **Rotate the Postgres password** in `.env` (it shipped in an earlier bundle).
- [ ] **Redeploy the VPS** with the current `Caddyfile` (adds the `wss://talacore.app/ws` route) and `scripts/start-tala-vps.sh` (binds 8765 and 8332 to loopback behind Caddy). Until then, updated desktops cannot reach the node.

*Once all boxes are checked, the Native Transparent Deployment path is certified for release.*
