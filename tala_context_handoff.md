## What Tala is
A self-hosted, provider-agnostic AI agent runtime: Electron shell + Python JSON-RPC backend (`ws://127.0.0.1:8765`) + a custom local Node.js PoA blockchain (`blockchain/src/app.js`, `http://127.0.0.1:8332`) + Postgres for durable state + HTML "Neural Node" files as memory/docs/skills. Meant to federate with other Tala instances over P2P and meter cross-peer compute via an on-chain token economy.

## Honest capability assessment (asked for directly, answering straight)
**Question was: does Tala have the capability surface to be a top-of-line agent, independent of which model is plugged in?**

Answer: **yes on breadth, not yet on proven reliability.**

- Breadth is real and verifiable, not a guess: `system.capabilities` (see below) reports **183 RPC methods across 47 subsystems + 55 agent-level tools**. Genuine differentiators vs. typical single-agent chat wrappers: persistent structured memory with governance/provenance metadata (HTML-NN, blockchain-anchored, not just a vector DB), a self-improvement loop with a bounded-patch + dry-run + validated-execution + risk-gate pipeline, and (as of this session) live capability introspection instead of hand-written docs that go stale. Multi-agent swarm/fleet primitives were a *claimed* differentiator through the first two passes of this session — the "Third pass" below found `swarm.start` was a complete no-op past its first DB write (nothing ever executed a node), fixed it, and proved a real topology now runs to completion end-to-end against the real DB; a real cross-node workspace-sharing gap in the underlying DAG engine remains open (see that section).
- The gap is *proven reliability of the harness connecting those capabilities to the model*, not capability count. Evidence from this single session: traced real conversations and found **5 distinct, fundamental bugs in the core tool-calling loop** (see changelog below) — not edge cases, first-conversation-you-try-it bugs. The provider-routing layer had a **completely inverted priority order** and a **timeout that failed 100% of real local requests**, both found and fixed today. The adversarial-conversation regression fixture (`tests/test_adversarial_conversations.py`) that would catch this class of bug in the future **was built today** — it's a start, not a track record. No published benchmarks, no external audit, solo-developer project with no peer review. The new MCP execution surface (see below) gates all 238 tools/methods behind one shared secret — broad, hours-old, unaudited.
- Bottom line for prioritization: don't add more capability surface next. Spend the next chunk of effort proving the existing surface is reliable under real use (more adversarial fixture coverage, more real conversations traced, tightening the tool-calling protocol) before treating this as production-grade.

## Second pass: extending the same method to self-improvement + memory (not yet committed)
Following the "capability breadth is real, reliability is unproven" conclusion above, the two subsystems called out as genuine differentiators but *never scrutinized* — the self-improvement bridge and the memory store/recall path — got the same real-code, real-DB (no mocking) treatment tool-calling got. Both had confirmed bugs on the first real pass, again not edge cases:

1. **`sdk/agent/safe_code_bridges.py::execute_self_improvement_goal`** (called by the `self_improvement.execute_goal` RPC/tool — the bridge a model actually uses to make Tala apply a change to itself):
   - **dry_run was silently forced to `True` on every call**, even when the caller explicitly passed `dry_run=False` asking for a real change. The plan was always built with `dry_run=True` hardcoded, and the final dry_run passed to execution was derived from that same hardcoded plan field instead of the caller's actual argument — so a model believing it had just made a real edit had, in every case, made none. Fixed by threading the caller's real `dry_run` straight through.
   - **Separately**, the function never accepted `replacements`/`file_writes`/`target_files` at all — for any goal not classified as "documentation" it always fell back to a synthetic no-op patch (old_text == new_text) on `README.md` and reported `success: true`, regardless of what the goal actually asked for. Fixed by threading `target_files`/`replacements`/`file_writes`/`validation_commands` through the function, the RPC handler, and the tool wrapper (`sdk/agent/tools.py`), and added a `no_op: true` field to the result so a caller that supplies no concrete change gets an honest signal instead of a false `success`.
   - New regression coverage: `sdk/agent/tests/test_safe_code_bridges.py` (23 tests, none mocked — real temp workspace via `monkeypatch.setattr(bridges, "WORKSPACE_ROOT", tmp_path)`), covering dry-run-must-not-touch-disk, real-run-must-actually-write, workspace escape/blocked-dir/blocked-extension containment, validation-command allowlisting, and the two bugs above (each test verified to fail against the pre-fix code, not just pass against the fix).

2. **`python/harness/memory.py`** — store/recall exercised against the real local Postgres dev DB (reachable in this sandbox; `tests/test_memory.py` exists but mocks `db.fetch`/`db.execute` everywhere, so it only ever proved the SQL text looked right, never that a stored fact is actually recoverable later):
   - **`handle_memory_browse` crashes on every single profile lookup**: `AttributeError: 'str' object has no attribute 'pop'` at the `config.pop("pii_vault", ...)` line, because asyncpg returns `JSONB` columns as raw JSON strings, not dicts, and this one code path (unlike every other place in the same file) was missing the `if isinstance(config, str): config = json.loads(config)` guard. Fixed.
   - **The auto-learning-cue feature ("remember that...", "from now on...", etc.) silently created memory that could never be found by default search.** Learning nodes get indexed with `source_type="documentation"` (their HTML-NN node type), but `handle_memory_search`'s default `sources` list was `["session", "task", "node", "workflow", "profile"]` — "documentation" was never in it, and neither was it in `handle_research_unified_search`'s equivalent default. So the entire "durable learning" capability — one of the claimed differentiators — worked end-to-end right up until the last step, then was invisible unless a caller happened to explicitly pass `sources=["documentation"]`, which nothing does. Fixed by adding `documentation`/`program-doc`/`function-doc` to both defaults.

## Third pass: swarm/fleet orchestration — confirmed and fixed the predicted gap
Picked up the "next candidate" flagged above. Confirmed the worst-case guess: `SwarmEngine.evaluate_edges` (`sdk/agent/swarm_engine.py`) was **never called from any production code path** — grep across the whole repo turned up zero callers outside its own definition and its unit tests. `swarm.start` → `SwarmEngine.spawn_topology` wrote a parent row and the start-node rows into `tasks` and returned; nothing ever consumed a 'pending' swarm-node row, executed it, or called `evaluate_edges` to advance the graph. A started swarm sat at "pending" forever — not a partial bug, a complete no-op past the first DB write. (`sdk/agent/queue.py`'s `BatchQueue.get_next_runnable_task` and `PersistentExecutionLoop` — the only other plausible consumer — are equally dead: also zero production callers, confirmed by the same grep.)

Fix, all in `sdk/agent/swarm_engine.py`:
- Added `SwarmEngine.execute_node_task()` — actually runs a node's work through `DAGExecutionEngine.execute_task_as_dag` (the one execution substrate in this codebase with real production mileage, already used by `GoalEngine.run_goal`), persists the result via `BatchQueue.transition_task`, then calls `evaluate_edges` to advance the graph. Never raises past its own boundary — all failure paths (including a crashed DAG run) still degrade to a failed-result gate evaluation so a topology's `failure_policy` (retry/`route_to`/`requires_human`→blocked) gets a chance to run instead of leaving the branch silently stuck.
- Wired the trigger into all three places a node can become runnable: `spawn_topology`'s start-node enqueue, `evaluate_edges`'s success-path enqueue of the next node, and its `route_to` retry-fallback enqueue. Each is gated on `cls._db_available()` (same `db.get_pool()`/`RuntimeError` guard pattern used everywhere else in this module) specifically so the existing fully-mocked unit tests (no live pool) don't spawn real background execution — verified this keeps `sdk/agent/tests/test_swarm_engine.py`'s existing assertions valid unchanged.
- Found and fixed a second, independent bug while building the real-DB regression test below: `evaluate_edges`'s terminal-node branch wrote the synthesis result via a raw `db.execute("UPDATE tasks SET result = ...")` and *then* called `BatchQueue.transition_task(..., )` with no `result` kwarg — `transition_task`'s own UPDATE always writes its `result` param, defaulting to `{}` when omitted, so that second call silently clobbered the just-written synthesis output. The parent task's persisted `result` was `{}` on every swarm run, forever. Fixed by passing `result=final_synthesis` straight into the `transition_task` call and dropping the now-redundant separate write. Confirmed the pre-fix code fails the new test's `result.get("output")` assertion; confirmed the fix passes it.
- New coverage: `tests/test_swarm_orchestration_e2e.py`, real DB (`init_pool`/`close_pool`, no mocking of `BatchQueue`/`db`), two tests — one drives a real 2-node topology through `spawn_topology` and polls the DB until the parent task reaches `complete` (asserting both node rows actually ran and the parent's `result` carries the real synthesis output, not `{}`), the other confirms a `requires_human` gate failure halts to `blocked` and the unreachable downstream node never executes. `DAGExecutionEngine.execute_task_as_dag` and `SynthesizerWorker.synthesize` are mocked in both — this test's job is proving the graph-progression *wiring* is real, not grading model output (that needs a live-provider test, not attempted here). Also updated `sdk/agent/tests/test_swarm_engine.py::test_evaluate_terminal_node`, whose old assertion (`mock_execute.call_count > 0`) was checking for the clobbering write's side effect and had to change to match the fix.
- Verified clean: `python -m pytest tests --ignore=tests/benchmarks --ignore=tests/test_integration_flow.py --ignore=tests/test_ghost_persistence.py --ignore=tests/test_adversarial_conversations.py` → **194 passed** (192 prior baseline + 2 new e2e swarm tests), 0 regressions. `sdk/agent/tests` run standalone (excluding the pre-existing `test_retrieval.py` collection error, unrelated) → 45 passed, 1 pre-existing unrelated failure (`test_goal_engine.py::test_run_goal_success`, already documented above as a DB-pool-ordering issue when that directory runs standalone).
- **Follow-up in the same pass, prompted directly by the user:** the initial version of this fix let `DAGExecutionEngine` spin up its default per-node git worktree/branch (`git worktree add … -b tala-task/<task_id>`, via `handle_task_create_worktree`) — flagged above as a design gap because a fresh worktree branches off the last commit, not a sibling node's uncommitted merge, so cross-node file visibility wasn't reliable. User's instruction was explicit: swarm nodes are supposed to work without any external services like git worktrees at all. Fixed properly (not worked around) in `SwarmEngine.execute_node_task`: it now pre-sets `task_item.worktree_path = engine.root_dir` before calling `execute_task_as_dag`. `execute_task_as_dag` only attempts its DB-lookup-then-auto-`git worktree add` sequence when `worktree_path` is falsy on the incoming task, so this short-circuits that entirely — every swarm node now runs directly against the shared local workspace, no `git` subprocess, no branch, no merge-back step (the merge-back is a no-op because the "written" path and the "destination" path are already the same directory), and — as a direct side effect — this also *closes* the cross-node visibility gap: node N+1 sees node N's file writes immediately since there's only ever one shared directory, not per-node worktree copies. New regression: `sdk/agent/tests/test_swarm_engine.py::test_execute_node_task_skips_git_worktree` asserts `handle_task_create_worktree` is never called and that the `TaskItem` handed to `DAGExecutionEngine.execute_task_as_dag` always has `worktree_path` pre-set. Full suite re-verified green after this change (see below). `PortRouter` port-allocation bookkeeping was left as-is — it's local in-process/DB coordination, not a git-style external dependency, and the user's objection was specifically about git worktrees.
- **Separately flagged, not fixed:** `DAGExecutionEngine.execute_task_as_dag` imports `unregister_active_task` alongside `register_active_task` but only ever calls the latter — `sdk.agent.goal_engine._ACTIVE_TASK_IDS` grows and never shrinks, which makes `ZombieReaper.reclaim_zombies` (`sdk/agent/swarm_engine.py`) permanently skip reclaiming any task_id that was ever registered. Spun off as a separate background-task suggestion rather than fixed inline (out of scope for this pass, small and isolated).

## Architectural design gaps still open (carried forward, not touched this session)
1. **Blockchain lineage/attribution** — `/chain/reconcile` does simple longest-chain-wins replacement; the intended design is git-commit-style attribution-preserving forks. Undesigned.
2. **Ghost chain vs. remote chain should be two separate ledgers**, not one `Blockchain` class playing both roles. The push-side privacy leak was fixed in the prior session; the **pull-side risk (remote chain overwriting local ghost history) is still open**.
3. **Literal LoRA activation** — `python/inference/lora_trainer.py` queues JIT LoRA training keyed to node activation score, but `is_peft_available()` is false (PEFT/TRL not installed), so it only simulates training.
4. **Federation is architecturally scaffolded, not demonstrated** — no evidence of two live Tala instances actually federating end-to-end over the P2P/blockchain layer.
