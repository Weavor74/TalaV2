Tool: describe_architecture

<p><strong>describe_architecture</strong> is a callable tool in Tala's registry. Read this system's architecture contract: what its terms mean here, which common assumptions do NOT hold, and where its data actually lives. Call this before reasoning about how the system is built, especially before writing a health check, a migration, or a backup.</p><p>Call it as <code>describe_architecture(section)</code>, where <code>*</code> marks a required argument:</p><ul><li><code>section</code> (string, optional)</li></ul><p>Tala does not follow several ordinary conventions -- memory is the HTML-NN store rather than a database, the data root travels with a portable install rather than living in an OS profile directory, and a configured provider is not a working one until probed. A model applying default assumptions produces conclusions that look correct and are not. That has already happened here: a health check for "memory" was written against the assumption that memory means a database service, and reported healthy while never looking at the store that actually holds the nodes. Prose describing the architecture existed and did not prevent it, because prose answers a reader who has already decided to look. This returns the same information as a contract a caller can be pointed at before it starts guessing.</p><p>Implemented in <code>sdk.agent.tools</code>. The Python registry remains what actually executes; this node is the catalogue entry that makes the tool retrievable and referenceable from a workflow.</p>
