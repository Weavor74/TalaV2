Semantic Memory

LoRA is not implemented or used in this stack. No adapter is shipped, selected for serving, or applied: Ollama's API has no adapter parameter, neither do the remote services, and the previous adapter (fitted to a non-US-origin base model) was removed from the repository by decision. What follows is the procedure that would apply if an adapter were ever trained against a base that actually serves chat; treat it as a reference, not as a working feature.

This used to fail silently. The harness logs a warning naming any adapter it selected and could not apply, so the gap is visible in the moment rather than inferred months later.

Why per-turn swapping is not available here

Ollama loads a model once and serves it. There is no request-level adapter field, so an adapter has to be part of the model the server already has. That makes swapping an adapter per recalled node impossible on this provider — and it is a reasonable constraint to design around rather than fight, because a voice adapter is a persona-level thing, not a per-document thing. One adapter per persona is the right granularity anyway.

The procedure

  1. Train. python scripts/train_voice_adapter.py --train writes a peft adapter (adapter_model.safetensors plus adapter_config.json).
  2. Convert to GGUF. Ollama consumes GGUF, not safetensors. llama.cpp ships convert_lora_to_gguf.py for exactly this:
    python convert_lora_to_gguf.py --base <base-model-dir> --outfile tala-voice.gguf <adapter-dir>
  3. Write a Modelfile naming the base model and the adapter:
    FROM llama3.2:3b
    ADAPTER ./tala-voice.gguf
  4. Create the variant. ollama create tala-voice -f Modelfile
  5. Point the provider at it. Set the local provider's model to tala-voice in Settings. Nothing else in the harness changes; adapter selection keeps running and keeps being informational on this path.

The constraint that decides the base model

The adapter and the model it is baked into must share the same base. The corpus trainer defaults to unsloth/Llama-3.2-1B-Instruct (Meta, US-origin; the project rule is US-origin base models only). The chat stack serves gpt-oss-20b, Llama 3.1/3.2 and gemma3:4b as GGUF with no local HuggingFace weights. An adapter trained on the 1B base cannot be baked into any of those. Training for a chat model means fetching its HuggingFace weights first and passing --base. Trainer output goes to the gitignored lora-generations/voice-adapter, never into nodes/.

Hardware

The card is an RTX 3050 with 6GB. A rank-8 adapter on a 1B trains comfortably, and on CPU as well, only slower. A 3B or larger needs 4-bit loading and gradient checkpointing to fit, and the installed torch build is CPU-only (2.13.0+cpu), so CUDA requires reinstalling torch from the matching index before the training extra — installing it after will fight the resolved CPU build.

What to expect

  • A voice adapter changes cadence, register and habit. It does not add knowledge, and should not be judged on whether it does.
  • An adapter trained on a thin corpus overfits to the phrasing it saw. Grow the corpus before keeping one.
  • The variant is a separate Ollama model, so the base model remains available and switching back is changing a setting.
