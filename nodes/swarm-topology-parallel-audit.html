Swarm Topology: Parallel Audit Swarm

This node is the executable definition of the Parallel Audit Swarm, and it exists to exercise the one thing a chain cannot: real fan-out and a real join. When a run is started with topology_id 'swarm-parallel-audit', SwarmEngine reads the 'topology' object in this node's #node-state block and builds the run from it. Editing this node changes how the audit behaves on its next run.

The shape: scout scopes the work, then three surveyors run concurrently against the same workspace - one reading the implementation, one reading the tests, one reading the documentation and neural nodes. reconcile is a join: it has three incoming edges and does not run until all three surveyors have arrived, at which point it runs exactly once. report then writes the findings up.

The point of the split is disagreement. Asking one agent 'is this subsystem healthy' gets one narrative; asking three agents to describe it from the code, from the tests, and from its own documentation, and then reconciling them, surfaces the gap between what a system does, what it proves, and what it claims. reconcile is instructed to lead with the disagreements because that is where the defects live - a subsystem that is documented but untested, or tested but never called, reads as healthy from any single vantage point.

No failure_policy is defined, which is deliberate: if a surveyor fails, its branch halts rather than retrying, the join never completes, and the run finalises with whatever did finish. The synthesis explicitly includes failed nodes, so a dead branch shows up in the report as a missing dimension instead of quietly narrowing the audit.

Rules for editing: node ids must be lowercase tokens and unique; every edge must reference nodes defined in this same spec; the edge graph must stay acyclic (backward movement is expressed with failure_policy.route_to, bounded by max_retries, not with an edge); and every edge condition must name a rule GatedVerifier actually implements, otherwise that branch could never advance. Adding a fourth surveyor means adding both its scout edge and its reconcile edge - add only the first and it runs but is never waited for; add only the second and the join waits forever on a node nothing dispatches.

Agents

  • scout (planner) — Scope the audit and state what each surveyor should look for
  • survey-code (researcher) — Survey the implementation: what the code actually does
  • survey-tests (researcher) — Survey the tests: what is actually proven, and what is only asserted
  • survey-docs (researcher) — Survey the docs and neural nodes: what the system claims about itself
  • reconcile (reviewer) — Reconcile the three surveys and name every place they disagree
  • report (documenter) — Write the audit findings up, disagreements first

Edges

  • scout → survey-code gated on success
  • scout → survey-tests gated on success
  • scout → survey-docs gated on success
  • survey-code → reconcile gated on success
  • survey-tests → reconcile gated on success
  • survey-docs → reconcile gated on success
  • reconcile → report gated on success
