Semantic Memory

LoRA adapters exist to shape Tala's voice and behaviour, not her knowledge. An adapter fitted to a few kilobytes of prose learns cadence, register and habit. It does not learn facts, and aiming it at facts would build a worse version of the retrieval path, which is better at recall at every scale. The node schema already names this axis: data-weight-behavior-influence.

What the training data is

The pre-Weavor story corpus under data/training_corpus/. Each story is itself an HTML Neural Node, and inside <section id="episodic-memory"> it carries turns marked <div class="turn" data-speaker="tala" data-emotion="...">. Every one of Tala's turns opens with the literal prefix [Emotional State: X].

That prefix is preserved verbatim in training, never stripped. It is the exact surface form python/harness/memory.py writes into RP conversation memory, so an adapter trained without it would produce output that does not match its own memory format. Some turns also carry a <pre class="tool-call"> block, which is kept for the same reason: voice, emotion and tool habit are one behaviour, and splitting them across three mechanisms would teach them apart.

Only turns where data-speaker is tala are used. Training on the interlocutor's lines would teach her to write them.

The trainer

scripts/train_voice_adapter.py. Two modes:

  • --dry-run reports the dataset — example count, character and token totals, era and emotion distribution, how many turns carry a tool call — and needs no training libraries. Use it to judge whether the corpus is worth training on before spending anything.
  • --train tokenises at max length 512, applies LoraConfig(r=8, lora_alpha=16, dropout=0.05) targeting q_proj and v_proj only, and trains with batch size 1 and gradient accumulation 4 at learning rate 2e-4.

Attention projections alone are targeted because voice lives in how attention is distributed, and a narrow target keeps the adapter small enough to be worth swapping per turn.

The default base model is unsloth/Llama-3.2-1B-Instruct, the ungated mirror of Meta's Llama 3.2 1B Instruct: US-origin (the project rule is US-origin base models only) and small enough to train on CPU. The chat stack serves gpt-oss-20b, Llama 3.1/3.2 and gemma3:4b through llama.cpp and Ollama as GGUF, so an adapter trained on this 1B base does not match any of the models that actually answer.

What is real and what is not

LoRA is not implemented in this stack, and no adapter has ever affected a token of Tala's output. Stated plainly because the system used to claim otherwise.

  • python/inference/lora_trainer.py never trained anything. Without peft it wrote the ASCII string DUMMY_LORA_WEIGHTS_FOR_<node_id> to a .safetensors path; with peft it executed a bare pass. The queue then logged "Successfully trained LoRA" over both. It now raises LoraTrainingUnavailable instead of reporting success.
  • The one real adapter ever produced, fitted to a non-US-origin base model, was deleted from the repository by decision. It is not replaced: no adapter is shipped, selected for serving, or applied by any provider in the current stack.
  • scripts/train_voice_adapter.py remains as an offline experiment tool. Its output goes to lora-generations/voice-adapter, which is gitignored, so a trained adapter is never committed or mistaken for part of the product.

What would make it real

  1. Install the training libraries: peft, trl, transformers, accelerate. All install on Windows, unlike vLLM.
  2. Grow the corpus. At the time of writing it yields 25 turns, roughly 2,000 tokens — enough to prove the pipeline, far too thin for an adapter worth keeping. scripts/generate_stories.py produces more.
  3. Train against a base that is the model actually serving chat, and decide where the adapter is applied. Ollama can bake an adapter into a named model variant through a Modelfile ADAPTER directive, which suits a small number of persona adapters but not one per node. Until then, treat any adapter as unused.

Common wrong answers

  • Adapters are not used: none is trained, shipped or applied in this stack, and the old adapter was removed.
  • Training does not teach facts, and should not be used to.
  • Node weights do not currently select an adapter that anything applies; see system-html-nn-activation-weights for what they do drive.
