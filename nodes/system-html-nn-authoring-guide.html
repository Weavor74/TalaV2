Semantic Memory

Tala authors HTML Neural Nodes by preparing a structured node specification and passing that specification through a deterministic generator and validator. Tala must not invent raw node wrappers, must not use a custom <node> element, and must not report success until a file exists on disk and parses successfully.

The root format is an HTML document containing a parser-readable <article> element with data-node-id, data-node-type, and data-execution-authority. Documentation nodes use data-node-type="documentation", zero execution authority, zero memory authority unless explicitly justified, and source metadata that explains what files or sources produced the node.

This guide describes how to author safe documentation, workflow, validator, and director-aware nodes. It is context-only. It does not grant Tala permission to execute tools, write files, alter settings, approve governance, change providers, access private vault content, or create persona/backstory/history nodes.

Authoring Workflow

  1. Identify the node purpose, target, and allowed node type.
  2. Collect source files or source documents that justify the node.
  3. Load any required reference nodes declared by a director block.
  4. Compute a source fingerprint from those inputs.
  5. Create a structured node specification with title, type, target, source metadata, semantic content, relationships, director rules, and state data.
  6. Use the approved Python generator to render the specification into the canonical <article> HTML-NN format.
  7. Write the file to the runtime-resolved active node directory.
  8. Parse the written file with Tala's parser.
  9. Verify schema fields, authority boundaries, relationship weights, JSON blocks, and forbidden content.
  10. Only then report created, updated, unchanged, stale, or error counts.

Structured Node Specification

A generator input should be a data object, not freeform HTML. A documentation node specification should include these fields:

  • node_id: stable kebab-case identifier.
  • node_type: documentation for program documentation.
  • title: human-readable title matching h1#node-title.
  • doc_target: the panel, category, schema, or feature being documented.
  • source_files: files or source documents used to generate the node.
  • source_fingerprint: hash over the relevant source inputs.
  • semantic_memory: clear prose that explains what the node means.
  • relationships: typed weighted links to related nodes.
  • directors: optional inert JSON instructions for reference routing, workflow validation, request preparation, or audit summaries.
  • state_data: JSON object for structured metadata, tags, sections, and verification results.

Director Authoring

Director blocks let an HTML-NN act as a scripted coordinator without becoming an unsafe executable payload. Tala may use a director to reference other nodes or documents, collect required information, validate workflow readiness, prepare an MCP/RPC request, or record an audit summary.

Director blocks must be JSON-only and inert. Use type="application/tala-director+json", declare data-script-kind, and declare data-side-effects as none or request-only. A director may request a registered bridge such as docs.generate_program_nodes, but the bridge performs the action only after normal authority and policy checks.

<script type="application/tala-director+json"
        id="director-generate-program-docs"
        data-script-kind="workflow"
        data-side-effects="request-only"
        data-tool-target="docs.generate_program_nodes">
{
  "when": { "intent": "generate_program_documentation" },
  "reference": [
    { "type": "html-nn", "node_id": "system-neural-node-v2-schema", "required": true },
    { "type": "html-nn", "node_id": "system-html-nn-authoring-guide", "required": true }
  ],
  "collect": [
    "panels",
    "settings_categories",
    "workflow_screens",
    "chat_tools",
    "vault_profile",
    "logs_diagnostics"
  ],
  "validate": [
    "source paths are runtime-safe",
    "node_type is documentation or program-doc",
    "execution authority is zero for documentation nodes",
    "director side effects are none or request-only"
  ],
  "submit": {
    "target": "mcp:docs.generate_program_nodes",
    "mode": "request",
    "requires_user_confirmation": true
  }
}
</script>

Active Node Directory

Nodes must be written to Tala's active Electron user-data node directory, resolved at runtime. Do not hardcode a machine-specific absolute path in generator code.

  • Electron main process: path.join(app.getPath("userData"), "nodes").
  • Python backend: use Path(os.environ["TALA_USER_DATA"]) / "nodes" when TALA_USER_DATA is available.
  • Fallback Windows: %APPDATA%/tala-engine/nodes.
  • Fallback macOS: ~/Library/Application Support/tala-engine/nodes.
  • Fallback Linux: ${XDG_CONFIG_HOME:-~/.config}/tala-engine/nodes.

Security Boundaries

  • Do not include executable JavaScript in generated nodes.
  • Use script type="application/json" for inert state data blocks.
  • Use script type="application/tala-director+json" only for inert director blocks.
  • Do not create or endorse script type="application/x-python" executable blocks for documentation nodes.
  • Do not include private profile data, vault contents, credentials, API keys, personal backstory, roleplay memory, persona history, or LTMF-derived content.
  • Do not assign documentation nodes operational authority. Use data-execution-authority="0.00".
  • Do not allow a node to grant itself tool access, file-write permission, provider-change permission, wallet permission, or governance approval.

Validation Checklist

  • File exists in the active node directory.
  • Parser finds one root <article>.
  • data-node-id, data-node-type, and data-execution-authority are present.
  • data-node-type matches the intended type.
  • data-execution-authority is numeric and within 0.00 to 1.00.
  • Documentation nodes include data-doc-target, data-source-files, data-source-fingerprint, and data-generated-at.
  • All JSON state and director blocks parse as JSON objects.
  • Director blocks declare valid kind, side effects, references, validation rules, and optional registered request targets.
  • Relationship weights are within 0.00 to 1.00.
  • No forbidden private or personal content appears in generated program documentation.
  • Generator reports success only after disk verification passes.

Self-Healing Rules

Self-healing documentation compares the current source fingerprint to the fingerprint stored in the existing node. If the fingerprint matches, leave the node unchanged. If the fingerprint changes, regenerate and validate the node. If a documented target disappears, mark the node stale or archive it rather than silently deleting it.

A self-healing director may reference the canonical schema, authoring guide, and source files; collect current panel or settings metadata; validate staleness; and submit a request to a registered documentation generator. The director itself must not write files or call external systems directly.
