Semantic Memory

Tala is an offline-first, desktop-native AI orchestration shell. The Electron main process owns the window, preload bridge, persistent terminal process, local Python harness process, and WebSocket relay. The renderer presents the working surfaces: neural nodes, research, browser, blockchain ledger, vault, contacts, settings, logs, mission control, agent builder, workflows, profiles, and terminal output.

The Python harness is the central JSON-RPC backend. It exposes inference, database access, token accounting, graph activation, vault status, provider settings, agents, profiles, workflows, MCP servers and tools, search, logging, research, tasks, swarm execution, gateway status, plugins, repo tools, shell execution, code generation and repair, test validation, self-improvement, wiki operations, heartbeats, memory search, and unified research. This RPC layer is the operational spine used by the desktop UI and internal workflow execution.

Durable authority is PostgreSQL. Runtime configuration and user-modifiable surfaces are stored as database rows, then important settings are mirrored into private HTML Neural Nodes so Tala can read its own configuration as governed memory. HTML-NN files are not passive notes: they carry semantic memory, relationships, authority weights, trust metadata, privacy labels, state JSON, provenance, and optional inert director blocks.

The SDK under sdk/agent supplies the agent substrate: planner, dispatcher, queue, goal engine, governance gates, recovery, verification, scanner, linter, coder, shell, workflow compiler, telemetry, memory providers, safe code bridges, trust registry, and swarm engine. The SDK under sdk/gateway supplies plugin validation, permission checks, promptware redaction, lifecycle tracking, and gateway resolver behavior.

Tala is therefore closer to an agent operating environment than a single chat app. The correct mental model is a local cognitive engine with a desktop control room, configurable provider fabric, HTML-NN memory graph, workflow executor, and governed bridge layer for tools, shell, code, MCP, research, and external endpoints.

Runtime Layers

  • Electron main process: desktop lifecycle, security policy, Python harness spawning, WebSocket relay, terminal process, local file IPC, and blockchain process lifecycle.
  • Renderer: user-facing control surfaces for nodes, settings, workflows, research, logs, profiles, mission control, agent builder, and terminal panes.
  • Python harness: JSON-RPC backend, provider routing, inference, memory activation, workflow execution, MCP client manager, search, logging, profile sync, and task orchestration.
  • PostgreSQL: authoritative durable state for nodes, providers, profiles, settings, memory index, conversations, tasks, events, token ledger, credentials, contacts, and logs.
  • HTML-NN filesystem: governed memory and documentation graph stored as parseable HTML files in the active user-data nodes directory, with repo nodes used as development fallback.
  • SDK and gateway: reusable agent operations, governance, plugin manifests, promptware scanning, code bridges, repo tooling, telemetry, and swarm abstractions.

Comparison Position

Compared with Hermes Agent, Tala already owns many of the same conceptual primitives: desktop shell, configurable model/provider endpoints, MCP integration, memory, workflows, local tool execution, and admin surfaces. Tala's distinctive edge is the HTML-NN memory graph, where docs, settings, workflows, profiles, concepts, and system memories can share one governed node format.

The remaining maturity gap is mostly release discipline and productization: dependency health, first-run setup, packaged installers, self-update behavior, web/admin parity, onboarding copy, release smoke tests, tighter CI, and explicit documentation of the HTML-NN-centered architecture.

Operational Guidance

  • Treat python/harness/server.py as the live RPC map until the methods are split into focused modules.
  • Treat python/harness/db.py as the schema map for what Tala considers durable authority.
  • Treat nodes/*.html and the active user-data node directory as first-class documentation and memory, not generated extras.
  • Treat provider settings as runtime data, not compile-time constants.
  • Treat gateway and governance modules as the boundary between trusted core operations and untrusted plugins, MCP servers, shell commands, and external endpoints.
