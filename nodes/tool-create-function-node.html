Tool: create_function_node

<p><strong>create_function_node</strong> is a callable tool in Tala's registry. Author an HTML-NN that carries executable Python. The node is written and recorded but NOT admitted to run: a person reviews the code and admits it before it can execute.</p><p>Call it as <code>create_function_node(node_id*, title*, code*, description, timeout_seconds)</code>, where <code>*</code> marks a required argument:</p><ul><li><code>node_id</code> (string, required)</li><li><code>title</code> (string, required)</li><li><code>code</code> (string, required)</li><li><code>description</code> (string, optional)</li><li><code>timeout_seconds</code> (string, optional)</li></ul><p>Writes a `function` node whose node-state block holds `code`, and records its arrival as locally authored. It cannot run yet. Authoring does not admit, even here. The obvious shortcut is to treat locally written code as reviewed -- you wrote it, after all -- but this tool is in the registry, so the writer is as often the model as the person, and self-admission would make "never a start without review" true only for code that came from elsewhere. That is precisely backwards: code Tala writes for herself is the case the review exists for. So the flow is the same for everyone. Write, read, admit. The code runs with `call_tool(name, **kwargs)` in scope, `inputs` bound to whatever the caller passed, and `return` for its value -- the same contract as run_tool_script.</p><p>Implemented in <code>sdk.agent.node_execution</code>. The Python registry remains what actually executes; this node is the catalogue entry that makes the tool retrievable and referenceable from a workflow.</p>
