Semantic Memory

The Program Documentation Generator creates HTML Neural Nodes that document Tala's program structure. It is an intentional workflow, not an automatic startup task and not a persona or private memory generator. Generated nodes describe panels, settings categories, workflow screens, chat tools, vault/profile behavior, neural nodes, logs/diagnostics, blockchain/ledger surfaces, and search/research features.

The generator is invoked only through approved entry points: the Settings System action labeled Generate Documentation Nodes, the slash command /generate-doc-nodes, or the registered RPC/MCP-style bridge docs.generate_program_nodes. A director block may prepare a request, but the actual generator must run through the trusted bridge and policy checks.

Every generated documentation node must use the canonical <article> HTML-NN v2 format, mark itself as documentation or program-doc, carry zero execution authority by default, include source metadata and fingerprints, parse successfully after writing, and exclude private profile data, credentials, vault contents, persona history, roleplay memory, and LTMF-derived content.

Entry Points

  • UI: Settings -> System -> Generate Documentation Nodes.
  • Command: /generate-doc-nodes.
  • Bridge: docs.generate_program_nodes.

Generation Scope

The generator scans program structure and creates one documentation node per meaningful panel, category, or feature area. It should prefer granular nodes over a single giant reference node.

  • neural-nodes: node grid, filtering, node metadata, validation state, and graph relationships.
  • chat-tools: chat panel, slash commands, tool-call affordances, and safe bridge behavior.
  • workflow: workflow builder, executor, validation, run history, and step status.
  • settings: one node per settings category, including system, model/provider, UI, memory, privacy, and diagnostics categories when present.
  • vault-profile: documented behavior only; no private profile payloads, secrets, or vault contents.
  • logs-diagnostics: log panels, doctor checks, error surfaces, benchmark/status views, and troubleshooting actions.
  • blockchain-ledger: visible ledger panels, verification concepts, and non-secret configuration surfaces.
  • search-research: search panels, research flow, source capture, and evidence display behavior.

Input Contract

The bridge receives a structured request object. Source paths must be repo-relative or runtime-resolved app paths. The request must not contain machine-specific absolute output paths.

{
  "targets": ["panels", "settings", "workflow", "tools", "vault-profile", "nodes", "logs"],
  "mode": "create-or-update",
  "output": {
    "directory": "active-user-data-nodes",
    "resolution": "electron-userData-or-TALA_USER_DATA"
  },
  "node_type": "documentation",
  "schema_version": "neural-node/v2",
  "require_confirmation": true,
  "validate_after_write": true,
  "archive_stale": false
}

Output Contract

The generator returns a summary that is based on files that were actually written and parsed. It must not report success from an intended plan alone.

{
  "created": 0,
  "updated": 0,
  "unchanged": 0,
  "stale": 0,
  "errors": [],
  "nodes": [
    {
      "node_id": "program-doc-settings-system",
      "path": "active-user-data-nodes/program-doc-settings-system.html",
      "doc_target": "settings.system",
      "source_fingerprint": "sha256:...",
      "validated": true
    }
  ]
}

Workflow Contract

  1. Resolve the active node directory at runtime.
  2. Load system-neural-node-v2-schema and system-html-nn-authoring-guide.
  3. Scan source files for panels, settings categories, routes, commands, tool bridges, and diagnostics surfaces.
  4. Create a structured specification for each documentation target.
  5. Compute a source fingerprint from the source files and relevant extracted structure.
  6. Render canonical HTML-NN v2 using the approved generator.
  7. Write nodes into the active node directory only.
  8. Parse each written file with Tala's parser and validate director JSON blocks.
  9. Compare existing fingerprints to mark nodes created, updated, unchanged, stale, or errored.
  10. Return a verified summary and audit record.

Self-Healing Contract

Self-healing documentation means the generator can intentionally compare source fingerprints and refresh stale program documentation nodes when the app changes. Self-healing does not mean silent autonomous execution. Automatic regeneration must be disabled by default unless a user or explicit policy enables it.

  • If source fingerprints match, leave the node unchanged.
  • If source fingerprints differ, regenerate the node and validate the replacement before reporting updated.
  • If a target disappears, mark stale or archive according to request policy.
  • If validation fails, preserve the prior valid node when possible and report an error.
  • If source context is missing, stop and request the missing context rather than inventing documentation.

Safety Boundaries

  • Do not generate persona, backstory, roleplay, private profile, vault-content, credential, or LTMF-derived nodes.
  • Do not use absolute machine-specific output paths in generator code.
  • Do not run raw JavaScript, Python, shell commands, or network calls from node content.
  • Do not let a generated node grant itself tool authority, execution authority, file-write permission, provider-change permission, wallet permission, or governance approval.
  • Do not report created or updated unless the written file parses successfully.

Implementation Notes

  • Electron resolves output with path.join(app.getPath("userData"), "nodes").
  • Python resolves output with Path(os.environ["TALA_USER_DATA"]) / "nodes" when TALA_USER_DATA is available.
  • Fallbacks may map to platform user-data conventions, but generated metadata should describe the logical target rather than embedding one user's absolute path.
  • The registered bridge should own filesystem mutation; HTML-NN director blocks only prepare requests.
