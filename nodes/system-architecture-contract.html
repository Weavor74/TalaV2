Architecture Contract

<p><strong>Read this before reasoning about this system.</strong> This system does not follow several common defaults. Read the 'differs_from_default' entries before reasoning about it, and prefer the terms defined in 'vocabulary' over their usual meanings. Applying ordinary assumptions here produces conclusions that look correct and are not.</p><h3>What these words mean here</h3><ul><li><strong>memory</strong>: The HTML Neural Node (HTML-NN) store under nodes/. Not a database service. Nodes are the record; every index over them is derived and disposable.</li><li><strong>HTML-NN</strong>: A normal HTML document with one parser-readable <article> carrying identity, node type, execution and memory authority, semantic-memory prose, typed relationship anchors, and a JSON state block. It is simultaneously a document, a record, and — when it declares execution authority — a program.</li><li><strong>workflow</strong>: A chain of tool calls passing one step's output into the next, stored as an HTML-NN and executed from that node.</li><li><strong>tool registry</strong>: A collection of HTML-NN (tool-*.html), one per tool, carrying the argument schema. The Python functions are what execute; the nodes are the catalogue.</li><li><strong>vault</strong>: A tag on a node meaning its sensitive fields are encrypted at rest. Not a separate store.</li></ul><h3>Where ordinary assumptions fail</h3><ul><li><em>Assumption:</em> Memory is a database or vector service. <em>Reality:</em> Memory is the HTML-NN files. ChromaDB and the Postgres memory_index are both derived indexes and can be deleted and rebuilt from nodes/ without loss. <em>If assumed anyway:</em> Health checks, backups and migrations aimed at the database will miss the actual memory entirely.</li><li><em>Assumption:</em> The database is the source of truth. <em>Reality:</em> Nodes are. Postgres holds operational state (tasks, sessions, providers) and a full-text index; where both exist, the node is authoritative and the database is a fallback. <em>If assumed anyway:</em> Writes that go only to the database are lost on the next regeneration from nodes.</li><li><em>Assumption:</em> Application data lives in an OS profile directory. <em>Reality:</em> Tala is portable and runs from removable media on any OS. The data root is the install directory unless TALA_USER_DATA says otherwise. APPDATA, XDG and ~/Library are deliberately ignored. <em>If assumed anyway:</em> Data is written to whichever host machine it happens to be plugged into, and does not travel with the install.</li><li><em>Assumption:</em> A configured credential means a working service. <em>Reality:</em> Configuration and health are separate. A provider reads CONFIGURED until something probes it; only a probe produces OK or FAILED. <em>If assumed anyway:</em> Dead providers are reported as healthy, which is the single most common defect found in this codebase.</li><li><em>Assumption:</em> An empty result means nothing matched. <em>Reality:</em> It may mean a subsystem is not wired. Interfaces here are expected to distinguish 'found nothing' from 'could not look'. <em>If assumed anyway:</em> Wiring failures are indistinguishable from empty indexes and go unnoticed for months.</li><li><em>Assumption:</em> Local model output can be trusted to be complete. <em>Reality:</em> Inference is local-first by requirement; no remote model is called for the user's own reasoning.</li></ul><h3>Stores</h3><p>The system of record is the HTML-NN store: 349 node(s) under nodes/. The ChromaDB index holds 0 of them and is rebuildable from the files. The Postgres full-text index covers operational memory — sessions, skills, profiles — and is not the node store; asking it about nodes under-reports. Hindsight is an optional external daemon whose absence is not a fault.</p><h3>Which store owns what</h3><p>Authoritative, and not reconstructible from anything else:</p><ul><li><strong>Neural nodes: documentation, tools, skills, personas, settings, workflows, learning</strong> — nodes/*.html under the portable data root. REQUIRED. This is the system of record. If lost: Unrecoverable. Every index below can be rebuilt from these; none of them can rebuild these.</li><li><strong>Live operational state: tasks, agents, profiles, contacts, p2p_sessions, conversations, client_settings, credentials</strong> — PostgreSQL. REQUIRED. Not derivable from nodes. If lost: Enrolments, approvals, conversation history and provider configuration are gone. Nodes do not carry them.</li><li><strong>Key material: wallet signing key, credential encryption key, web token</strong> — vault/ (VAULT_PATH, default: the repository root). REQUIRED, and separately from the database. If lost: Encrypted columns become unreadable and this install's chain identity changes, so peers no longer recognise it.</li><li><strong>The ledger: blocks and anchored transactions</strong> — blockchain/data/chain.json plus the chain tables. REQUIRED. Append-only and not regenerable. If lost: The audit trail is gone. Ghost (local, everything) and Real (shared, external interactions only) are separate; losing Ghost cannot be repaired from Real.</li></ul><p>Derived, and safe to delete:</p><ul><li>memory_index (full-text over sessions, skills, profiles, documentation) — PostgreSQL, rebuildable from nodes/ and the operational tables.</li><li>ChromaDB vector index over nodes — on disk beside the data root, rebuildable from nodes/.</li><li>embeddings (pgvector) — PostgreSQL, rebuildable from the indexed source rows.</li></ul><p><strong>Known contradiction:</strong> Conversations live only in PostgreSQL. The standing rule is that everything the harness creates or consumes is an HTML-NN. Conversations are an exception: rooms, participants and messages are database rows with no node behind them, so they are outside the node backup and invisible to node retrieval.</p><p><strong>Restore in this order:</strong> vault/ first — without the keys, encrypted columns restore as noise; nodes/ — the system of record; PostgreSQL — operational state; ledger files; derived indexes last, or not at all: let them rebuild.</p><h3>Security: three separate things</h3><ul><li><strong>Renderer isolation</strong> — The browser process. Page script cannot reach Node, the filesystem or other origins directly. Flags: contextIsolation=True, sandbox=True, nodeIntegration=False, webSecurity=True.</li><li><strong>The IPC surface</strong> — An unlisted channel is refused at preload. Dotted RPC method names must go through helpers.invoke, which remaps them to python:rpc without reopening a preload fallthrough. renderer/helpers.js remaps dotted method names to python:rpc; bare window.tala.request/invoke of those names is rejected.</li><li><strong>Peer permission checks</strong> — What another install may ask of this one. (1) WebSocket admission class: local (vault token), peer (HMAC over the contact's shared secret), bootstrap (no credential, and only on a connection node, for enrolment alone). (2) Per-class method allowlists — an unrecognised class gets the empty set, so a missing label means trusted with nothing. (3) Contact status: only 'approved' permits direct interaction; 'pending' and 'denied' are refused and told apart. (4) Per-contact permission grants, all defaulting to False; asking is recorded as a request and grants nothing. (5) Persona nodes are never resolvable by a peer, ahead of any grant. Room membership is a separate, narrower permission: it lets a participant speak in that conversation and grants nothing outside it.</li><li><strong>Host command execution</strong> — shell.run executes with the privileges of the user running the harness, in the repository root. Risk classification runs and is LOGGED; it does not block. The halt switch can refuse execution, and that is the only gate on this path. The renderer being OS-sandboxed says nothing about the harness, which is not. Treat 'Tala is sandboxed' as false.</li></ul><h3>How work reaches a tool</h3><ul><li><strong>chat</strong> (python/harness/server.py::handle_inference_generate): the model emits a tool call; ToolRegistry.run_tool dispatches it. Verification: no automatic verification — the user reads the reply.</li><li><strong>goals (autonomous)</strong> (sdk/agent/goal_engine.py): decomposition into a DAG, then tool nodes executed by the graph engine. Verification: sdk/agent/goal_verification.py checks the stated acceptance criteria.</li><li><strong>workflows</strong> (python/harness/workflow_executor.py): steps declared in an HTML-NN; each step is a tool call, a branch, or another node. Verification: step status only; a failed step stops the chain.</li><li><strong>DAG / graph execution</strong> (sdk/agent/graph_engine.py): tool nodes in the graph. Verification: per-node status; execution gates apply to node steps.</li><li><strong>crews</strong> (python/harness/crews.py): each member runs as an agent with the shared registry. Verification: escalation on failure; no independent verification pass.</li><li><strong>swarms</strong> (sdk/agent/swarm_engine.py): workers claim nodes atomically and call tools directly. Verification: join barrier and in-flight counting decide completion.</li><li><strong>scheduled jobs</strong> (python/harness/heartbeat_scheduler.py): a job fires one of the routes above. Verification: whatever the fired route verifies.</li><li><strong>peer requests</strong> (python/harness/server.py::handle_relay_deliver): it does not — the p2p surface has no tool dispatch. Verification: n/a.</li></ul><h3>Maturity, with evidence</h3><p>implemented = the code exists; tested = a named regression covers it; live-verified = observed working outside this machine; experimental = present and not to be relied on; unavailable = absent or known broken.</p><ul><li><strong>Federation: enrolment, relay, rooms across installs</strong> — live-verified.
