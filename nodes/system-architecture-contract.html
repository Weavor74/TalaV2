Architecture Contract

<p><strong>Read this before reasoning about this system.</strong> This system does not follow several common defaults. Read the 'differs_from_default' entries before reasoning about it, and prefer the terms defined in 'vocabulary' over their usual meanings. Applying ordinary assumptions here produces conclusions that look correct and are not.</p><h3>What these words mean here</h3><ul><li><strong>memory</strong>: The HTML Neural Node (HTML-NN) store under nodes/. Not a database service. Nodes are the record; every index over them is derived and disposable.</li><li><strong>HTML-NN</strong>: A normal HTML document with one parser-readable <article> carrying identity, node type, execution and memory authority, semantic-memory prose, typed relationship anchors, and a JSON state block. It is simultaneously a document, a record, and — when it declares execution authority — a program.</li><li><strong>workflow</strong>: A chain of tool calls passing one step's output into the next, stored as an HTML-NN and executed from that node.</li><li><strong>tool registry</strong>: A collection of HTML-NN (tool-*.html), one per tool, carrying the argument schema. The Python functions are what execute; the nodes are the catalogue.</li><li><strong>vault</strong>: A tag on a node meaning its sensitive fields are encrypted at rest. Not a separate store.</li></ul><h3>Where ordinary assumptions fail</h3><ul><li><em>Assumption:</em> Memory is a database or vector service. <em>Reality:</em> Memory is the HTML-NN files. ChromaDB and the Postgres memory_index are both derived indexes and can be deleted and rebuilt from nodes/ without loss. <em>If assumed anyway:</em> Health checks, backups and migrations aimed at the database will miss the actual memory entirely.</li><li><em>Assumption:</em> The database is the source of truth. <em>Reality:</em> Nodes are. Postgres holds operational state (tasks, sessions, providers) and a full-text index; where both exist, the node is authoritative and the database is a fallback. <em>If assumed anyway:</em> Writes that go only to the database are lost on the next regeneration from nodes.</li><li><em>Assumption:</em> Application data lives in an OS profile directory. <em>Reality:</em> Tala is portable and runs from removable media on any OS. The data root is the install directory unless TALA_USER_DATA says otherwise. APPDATA, XDG and ~/Library are deliberately ignored. <em>If assumed anyway:</em> Data is written to whichever host machine it happens to be plugged into, and does not travel with the install.</li><li><em>Assumption:</em> A configured credential means a working service. <em>Reality:</em> Configuration and health are separate. A provider reads CONFIGURED until something probes it; only a probe produces OK or FAILED. <em>If assumed anyway:</em> Dead providers are reported as healthy, which is the single most common defect found in this codebase.</li><li><em>Assumption:</em> An empty result means nothing matched. <em>Reality:</em> It may mean a subsystem is not wired. Interfaces here are expected to distinguish 'found nothing' from 'could not look'. <em>If assumed anyway:</em> Wiring failures are indistinguishable from empty indexes and go unnoticed for months.</li><li><em>Assumption:</em> Local model output can be trusted to be complete. <em>Reality:</em> Inference is local-first by requirement; no remote model is called for the user's own reasoning.</li></ul><h3>Stores</h3><p>The system of record is the HTML-NN store: 228 node(s) under nodes/. The ChromaDB index holds 225 of them and is rebuildable from the files. The Postgres full-text index covers operational memory — sessions, skills, profiles — and is not the node store; asking it about nodes under-reports. Hindsight is an optional external daemon whose absence is not a fault.</p><p>Do not take this document's word for it. Call logging.get_system_health for measured subsystem state, tools.catalogue for the live tool list, and list_executable_nodes for what can actually be run. Each reports what it observed and on what basis.</p>
