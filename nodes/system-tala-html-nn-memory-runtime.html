Semantic Memory

HTML Neural Nodes are Tala's primary memory primitive. A node is a normal HTML document containing one parser-readable <article> with identity, type, authority fields, weights, trust metadata, privacy labels, semantic memory text, typed relationship anchors, JSON state, provenance, and optional inert director blocks. The semantic memory section is the main human-readable content that Tala searches, activates, injects, summarizes, and distills.

At inference time, Tala resolves the active nodes directory from TALA_USER_DATA, platform app-data paths, or the repo nodes fallback. It parses every valid .html node, filters settings nodes unless the prompt asks about settings/providers, filters agent-specific nodes by active agent tags, computes TF-IDF relevance over node ID, title, and semantic memory, then scores activation through the activation engine.

Activation is a product of semantic match, relevance weight, confidence weight, freshness, provider trust, and governance multiplier. Tala then propagates activation across typed relationship links for two hops using each relationship weight. Active nodes above the threshold are sorted and selected for prompt injection. In assistant mode, up to five active nodes can be injected as HTML Neural Net activated context. In roleplay or hybrid mode, up to two active memory nodes are cleaned and injected as first-person dynamic personal memories.

Workflow nodes participate in this same memory graph. When an active workflow node crosses the auto-evaluation threshold, Tala resolves the corresponding workflow JSON and executes or summarizes it before the model responds. Settings-type workflows collect live database snapshots so configuration answers come from current provider and settings tables rather than model guesses.

Tala also maintains a database-backed memory provider ecosystem. Conversation turns, task events, profiles, nodes, workflows, and distilled research can be indexed into memory_index and searched through PostgreSQL full-text search. A Hindsight provider can add external local context. Memory browsing applies promptware redaction and injection scanning before returning context.

HTML-NN Fields

  • data-node-id: stable node identifier used for retrieval, relationships, provenance, and UI display.
  • data-node-type: node category such as documentation, settings, workflow, concept, tool, memory, persona, or rule.
  • data-execution-authority: immutable authority value required by the parser; documentation nodes should remain zero.
  • data-memory-authority, data-provider-authority, data-wallet-authority, data-tool-authority: bounded influence markers for memory, providers, wallet operations, and tools.
  • data-weight-relevance and data-weight-confidence: retrieval and activation weights.
  • section#semantic-memory: primary textual memory content used for search and context assembly.
  • a[data-relationship-type]: typed weighted graph edges used for propagation and explanation.
  • script#node-state: JSON-only structured state parsed with json.loads.
  • script#adapter-packet and script#node-provenance: optional structured adapter and provenance metadata.
  • script[type="application/tala-director+json"]: inert JSON director instructions for reference routing, validation, request preparation, or audit, never direct execution.

Activation Flow

  1. Resolve active node directory from user-data, app-data, or repo fallback.
  2. Parse valid HTML-NNs with sdk.agent.parser.parse_file.
  3. Filter private or irrelevant node classes according to prompt and active agent tags.
  4. Build retrieval text from recent conversation context plus current prompt.
  5. Score TF-IDF relevance over node ID, title, and semantic memory.
  6. Compute base activation with ActivationEngine.score.
  7. Propagate activation across relationship anchors for two hops.
  8. Execute activated workflow nodes above the auto-evaluation threshold.
  9. Inject selected active semantic memory into the system prompt.
  10. Log injected node IDs, scores, and workflow collection events to the database.

Memory Index

The memory_index table is the local searchable text index for session, task, node, workflow, and profile memory. It stores source type, reference ID, title, content text, trust label, creation timestamp, and a generated PostgreSQL tsvector. Ranking boosts profiles, nodes, tasks, verified trust, profile trust, private trust when explicitly allowed, and recent entries.

HTML-NNs can be reindexed by parsing the file and storing their semantic memory, title, trust label, and relationships. Profiles can be chunked into identity/about, skills, projects, preferences, relationships, and private PII-protected memory chunks. Completed conversation turns are written to both conversation_turns and memory_index with duplicate control.

Governance Boundary

Activation selects context; it does not grant permission. A high-scoring documentation node can influence explanation, evidence, and retrieval, but it cannot authorize tool execution, shell commands, provider changes, vault reads, wallet actions, governance approval, or file writes. Mutations must pass through registered RPC, gateway, permission, promptware, and governance checks.

This node is documentation only and carries zero execution authority, memory authority, provider authority, wallet authority, and tool authority.
