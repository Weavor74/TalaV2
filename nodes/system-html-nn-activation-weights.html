Semantic Memory

Weights on an HTML Neural Node are static numbers stored as attributes in the node's own HTML file. They are not learned, not trained, and not updated by inference. They are read at parse time and multiplied together to decide how strongly a node activates for a given query. Nothing about answering a question changes them. This node exists because that mechanism was previously documented nowhere, and the gap was filled with plausible invention instead.

The weight fields

Every node declares these as data-* attributes, each clamped to the range 0.0 to 1.0 and parsed by sdk/agent/parser.py:

  • data-weight-relevance — how strongly this node's content should count when it matches. Read into weight_relevance.
  • data-weight-confidence — how much the content is trusted to be correct. Read into weight_confidence.
  • data-weight-behavior-influence — how much the node should shape behaviour rather than supply facts. Parsed and stored; it is not part of the activation product below.
  • data-weight-governance-importance — governance salience. Parsed and stored; also not part of the activation product.
  • data-execution-authority — whether this node is permitted to act. Documentation nodes are 0.00 and must stay so.
  • data-memory-authority — whether this node is permitted to be recalled into a prompt. These two are different permissions and conflating them is a known past defect: documentation generated with both at 0.00 became permanently unrecallable, because a zero here blocks activation entirely.

The activation formula

ActivationEngine.score() in sdk/agent/activation.py multiplies its inputs. There is no summation, no threshold function, and no learned component:

activation = semantic_match × relevance_weight × confidence_weight × freshness_weight × provider_trust_multiplier × governance_multiplier

Every input is clamped to 0.0–1.0 first, and the result is clamped again. Because it is a pure product, any single input of 0.0 makes the whole activation 0.0. That is deliberate for governance, which the engine documents as a hard gate.

In the live retrieval path, freshness_weight and provider_trust_multiplier are both passed as 1.0, so they currently have no effect.

What governance contributes

Governance is passed as a gate, not a ranking weight: 1.0 if either execution or memory authority is above zero, 0.0 otherwise. A node either may be recalled or may not; how well it matches decides its order. Passing the raw authority value instead made a node's permission double as its priority, so a document at 0.60 needed 1.67× the relevance of a settings node at 1.00 just to draw with it.

How semantic_match is produced

retrieve_relevant_nodes() in python/harness/retrieval.py queries a ChromaDB vector collection, converts cosine distance to similarity as 1 - distance, and returns raw_similarity × weight_relevance × weight_confidence.

Known defect: that return value is then passed to score() as semantic_match while weight_relevance and weight_confidence are also passed separately — so both weights are applied twice and act as squares. A weight of 0.5 contributes 0.25. This is currently masked because 113 of 115 nodes carry 1.00 for both, and 1.00 squared is 1.00. It matters the moment any node is given a non-default weight.

Propagation across relationships

After base activation is computed for every node, activation spreads along typed relationship links for two hops. Each hop applies ActivationEngine.propagate():

propagated = source_activation × relationship_weight × decay_factor, with decay_factor defaulting to 0.85.

A target node keeps the maximum of its own activation and any propagated value, so propagation can raise a node's activation but never lower it. Results below 1e-09 are floored to 0.0 to suppress underflow noise.

From activation to the prompt

Nodes scoring at least 0.01 are sorted by activation descending. The number injected depends on chat mode: 2 nodes in rp and hybrid, 5 in assistant. Their semantic memory is written into the system prompt. A node explicitly named in the message is pinned to the front at full activation, ahead of the ranked list.

What does change a weight

The adjust_behavioral_weights tool analyses feedback, shifts the relevance and valence values, and calls update_manifest to write them back into the node file. That is a deliberate edit to a document, not learning.

How the weights are meant to reach the model: LoRA adapters

This is the design intent, and it is only half built. The point of weighting a node is not merely to decide what text gets pasted into a prompt. It is that an activated node should temporarily modulate the model itself, by attaching that node's LoRA adapter for the turn.

The selection half exists and works. For each node chosen for injection, handle_inference_generate looks for an adapter: the node's own lora_adapter attribute if the file exists, otherwise nodes/<node_id>_lora/adapter_model.safetensors. The first one found becomes best_lora_path. If neither exists, queue_lora_training() is fired to compile one from the node's semantic memory. So activation — and therefore the weights — already decide which adapter should apply.

The application half does not reach the model in practice. best_lora_path is passed to exactly one provider, the embedded transformers engine, where peft attaches it. Ollama's API takes no adapter parameter, and the remote providers take none either, so on every provider actually in use the selected adapter is silently dropped.

Two things therefore stand between the intent and the behaviour:

  • Every adapter_model.safetensors on disk is a 37–51 byte placeholder, so there are no trained weights to apply even where the plumbing exists.
  • The one path that can apply an adapter is the embedded 0.5B, not the local Ollama model that serves normal chat.

The correct statement is therefore not "LoRA is unrelated to node weights". It is that node weights are intended to reach the model through adapters, that the routing from activation to adapter is built, and that no adapter has yet affected a single token of output on any provider.

Common wrong answers

  • Weights are not learned from the training-stories corpus.
  • Weights do not select or prioritise inference providers or models.
  • It is wrong to say weights have nothing to do with LoRA. They choose the node whose adapter is selected; the adapter simply never reaches the provider in use.
  • data-execution-authority values are decimals such as 0.60, never labels such as "high" or "medium".
  • There is no execution pipeline that processes higher-authority nodes first; authority gates recall, it does not order work.
